# Pruning proposal

2026-08-14. **Nothing has been deleted.** This document is the proposal; removals
happen in a later pass, one category per commit, CI green between each (D3).

**Headline: the only large win is the container image, and it is a big one.**
~3.1 GB of a 10.1 GB image is a model weight file stored **four times**, of which
one copy is loaded. Everything else on this list is small, and most of what was
examined should be kept.

**Second headline, and the more useful one: the audit's own method produced 44
candidates, of which 41 were false positives and 3 were real.** Every candidate
it generated by absence-of-match had to be individually disproved. That ratio is
the finding; it is recorded in full under
[The method's error rate](#the-methods-error-rate) rather than hidden, because it
is the reason D2 exists.

|---|---|---|
| `*.pdf`, `*.xlsx`, `*.pptx`, `*.traineddata` | binary corpus fixtures and OCR models | nothing — they are data, pinned by manifest hash |
| `frontend/tsconfig.tsbuildinfo` | generated build cache | nothing authored |
| untracked files (`node_modules/`, `__pycache__/`, `.next/`, `.env`) | not repository content; a hit there is a phantom | a real runtime dependency on a file nobody committed — but that would be a separate defect |

**Sources the file search cannot see, checked separately by other means:**

- **Extension → extractor dispatch** (`ExtractStrategy.__members__.get(ext)`) —

- **pytest collection by filename convention** — asked pytest

- **pydantic `Settings` env mapping** (`MIN_ANSWER_CHARS` → `min_answer_chars`)

- **Docker `CMD` / compose `command:`** — `uvicorn` and `arq` are invoked by

- **Runtime model-cache layout** — tested by deleting inside a throwaway

## 1 · Recommended removals

### R-1 · The duplicated reranker weights · ~3.1 GB · **HIGH VALUE**

**What.** `/opt/models` in the api/worker image is 4.2 GB. It holds the same
1,061 MB `bge-reranker-base` weight **four times**:

| path | file | loaded at runtime? |
|---|---|---|
| `models--BAAI--bge-reranker-base/blobs/15b9a8…` | `model.onnx` (fastembed tree) | **yes — this one** |
| `hub/models--BAAI--bge-reranker-base/blobs/15b9a8…` | `model.onnx` (hub tree) | no — duplicate |
| `hub/…/blobs/ced967…` | `model.safetensors` | no |
| `hub/…/blobs/5b475b…` | `pytorch_model.bin` | no |

The Dockerfile calls `snapshot_download()` (populating `HF_HOME=/opt/models` →
`/opt/models/hub`) and then constructs the fastembed classes, which populate
`FASTEMBED_CACHE_PATH=/opt/models` → `/opt/models/models--*` independently.
`snapshot_download` fetches *every* file in the repo, so all three weight
formats arrive; fastembed loads only ONNX.

**Evidence of non-use — measured, not reasoned.** In a throwaway container from
the shipped image:

```
before: 4.2G      after `rm -rf /opt/models/hub`: 1.1G

reranker scores   : [3.2634, -10.1945]   ordering correct
bm25 sparse       : works
verify_model_pins : exit 0, "sole cached snapshot" for BOTH repos
```

**And the scores are bit-identical**, which is what makes this pruning rather
than an R5 retrieval change:

```
unpruned: ['3.2633895874023438', '-10.194496154785156']
pruned  : ['3.2633895874023438', '-10.194496154785156']
```

**The protected guard is unaffected, and this was checked rather than assumed.**
`api/verify_model_pins.py` reads `CACHE / repo / "snapshots"` where
`CACHE = /opt/models` — i.e. the **fastembed** tree. It never looks at
`/opt/models/hub`. Its sole-snapshot semantics are preserved exactly; it was
re-run after the prune and still passes.

**Hazard removed.** A 43-minute build and a 10.1 GB image are the single largest
friction in the setup path, and this is 31% of the image for zero function.

**Risk if wrong.** Moderate and *detectable*, not silent. If some path resolves
the reranker through `HF_HOME` in a configuration not exercised here, the model
load fails loudly at startup — it cannot silently score differently, because the
only weight file left is the one already being loaded. The acceptance test is
`verify_model_pins.py` (build-time) plus a retrieval eval against
`tier-b-retrieval-2026-08-14.json`, which must come back `COMPARABLE` with
deltas of 0.000.

**Rollback.** Revert the Dockerfile line and rebuild. No repository content is
deleted; nothing is lost that a rebuild does not restore.

**Note on provenance.** Rebuilding changes `api_image_digest`, which is
**cosmetic** drift — the comparator will say so and still diff the metrics.

**Suggested shape** (do not apply in this pass):

```dockerfile
RUN python -c "…snapshot_download…" \
 && python -c "…fastembed constructors…" \
 && python /tmp/verify_model_pins.py "${BM25_REVISION}" "${RERANKER_REVISION}" \
 && rm /tmp/verify_model_pins.py \
 && rm -rf /opt/models/hub \
 && chown -R 10001 /opt/models && chmod -R a+rX /opt/models
```

`rm -rf` must be **inside the same `RUN`**, after verification — a separate
`RUN` leaves the 3.1 GB in the lower layer and saves nothing.

### R-2 · `frontend/tsconfig.tsbuildinfo` · 103 KB · LOW, but real

**What.** TypeScript's incremental build cache, committed once and by accident
(in `6638061`, a commit about startup guards — it is not mentioned in that
message). `"incremental": true` in `tsconfig.json` regenerates it on every build.

**Evidence of non-use.** Zero references across the full search path. Nothing
reads it; `tsc` writes it.

**Hazard removed — two, and the second is the real one.**

1. Any `tsc` run rewrites it, so it produces diff noise in unrelated commits.
2. `frontend/Dockerfile` does `COPY . .` in the build stage, so **a Windows
   developer's incremental cache is copied into the Linux image build**. Its
   `fileInfos` describe files as already-emitted; a stale entry can cause `tsc`
   to skip work it should redo. This has not been observed biting — it is a
   latent trap, not a live defect.

**Risk if wrong.** Essentially zero. Deleting it forces one full (not
incremental) type-check.

**Rollback.** `git revert`; or simply build, which regenerates it.

**Do at the same time:** add `tsconfig.tsbuildinfo` to `.gitignore` and to
`frontend/.dockerignore`. Deleting the file without ignoring it means the next
`npm run build` re-adds it.

### R-3 · `minio==7.2.15` from `requirements.in` · LOW

**What.** The MinIO Python SDK. Object storage is implemented with **boto3**
(`integrations/object_storage.py:6`) against the S3-compatible endpoint.

**Evidence of non-use.**

- Zero occurrences of `import minio` / `from minio` / `minio.` in any `.py`.
- The only `minio`-lowercase hits are `settings.minio_bucket` and friends —
  config field names for the *service*, unrelated to the SDK.
- Reverse-dependency check in the lockfile: `minio==7.2.15  # via -r
  api/requirements.in` — **nothing else requires it.** Compare `numpy`, which is
  `# via -r api/requirements.in, fastembed, llama-index-core, onnxruntime,
  pandas, qdrant-client` and therefore must stay.

**Hazard removed.** Same class as `requests`, removed earlier for exactly this
reason: a declared dependency nobody imports invites the reader to believe there
are two storage clients and to wonder which one is authoritative. That is
confusion at a decision point.

**Risk if wrong.** Low but non-zero — a hashed lockfile regeneration is required,
and that is the step that can surprise. The acceptance test is a full image
build plus the upload/ingest path end to end (upload → `queued → running →
completed`), because that is the only code that touches object storage.

**Rollback.** Restore the line, regenerate `requirements.txt`, rebuild.

### R-4 · Dead Docker images from deleted clean rooms · ~41 GB · **environment, not repository**

**What.** Images from the two clean rooms whose directories were removed at the
end of the verification pass, plus one orphan from the pre-refactor application:

| image | size | status |
|---|---|---|
| `final-verify-api`, `-worker`, `-web` | ~20.3 GB | source directory deleted |
| `cleanroom-audit-api`, `-worker`, `-web` | ~20.3 GB | source directory deleted |
| `knowall-documentbot-streamlit` | 900 MB | no such service in `docker-compose.yml`; predates the Next.js/FastAPI refactor by 4 weeks |

**Evidence of non-use.** `streamlit` appears in the search path only as
*history* — `RAG_EVOLUTION.md` describing the prototype it replaced, and
`REMEDIATION_LOG.md` recording the `pre-refactor-streamlit` tag. No compose
service, no Dockerfile, no CI reference. The two clean-room projects do not
appear in `docker compose ls`.

**Hazard removed.** Measured disk. This is the only item on the list with a cost
anyone has actually felt.

**⚠ Removal instructions, and read this part.** Delete **by explicit image ID**:

```sh
docker rmi 196a77e09fea 47ce268dddb7 3f4cb4a1ede4 \
           d40b688fcdc1 e93835f3eeac 2a3914b3b9e7 2bccc125fd2c
```

**Do NOT run `docker system prune -a` or `docker volume prune`.** This is no
longer a caveat on this item — it is filed as a **P1 operational hazard** in
`HANDOFF.md` §11, because it is true whether or not anything is ever pruned.
Summarised here only so this instruction is not followed in isolation. The
compose file declares its volumes with an explicit `name:` and **no project
prefix**:

```yaml
volumes:
  qdrant_data:
    name: qdrant_data      # not knowall-documentbot_qdrant_data
```

Two consequences. First, `qdrant_data`, `minio_data`, `ollama_data` and
`redis_data` are **shared by every compose project built from this file** —
which is why the clean rooms were never volume-isolated and why their data had
to be backed up and restored by hand. Second, there are 271 dangling volumes on
this machine and the live ones are indistinguishable from the dead ones by
naming convention alone. A blanket volume prune destroys the production
collection. **Prune volumes by name or not at all.**

The 116 GB `docker system df` reports as reclaimable spans unrelated projects on
this machine and is **not** a KnowAll figure. The KnowAll-attributable share is
the ~41 GB above.

## 2 · Behaviour changes — split out per D5

Not pruning. Each needs its own proposal and its own acceptance test. Listed here
only so they are not silently folded into a deletion commit.

### B-1 · `tests/test_ollama.py` and `tests/test_embedding.py` fire network calls during pytest **collection**

**Do not delete these. Rename or guard them.**

Both are named `test_*` but contain **module-level** code with no test function,
so pytest imports them and the module body executes. Measured:

```
$ pytest tests/test_ollama.py --collect-only -q
The capital of France is Paris.          <-- a REAL generation, during --collect-only
no tests collected in 1.05s
```

`pytest.ini` sets `testpaths = tests/unit`, so the default run never touches
them. But `pytest tests/`, or any future widening of `testpaths`, silently makes
an LLM call and an embedding call while merely *collecting*. In CI that is a
hang or a failure attributed to the wrong thing.

They are genuinely useful smoke checks and both **still work**, verified by
running them as documented. The fix is to stop them looking like pytest tests:
rename to `smoke_ollama.py` / `smoke_embedding.py`, or wrap the bodies in
`if __name__ == "__main__":`. Either is a behaviour change to the test surface,
so it is proposed, not done.

### B-2 · `tests/check_qdrant.py` is broken

It constructs `QdrantClient(host=…, port=…)` with **no `api_key`**, which
predates Qdrant authentication. Run today, as its own docstring instructs:

```
$ docker compose exec api python tests/check_qdrant.py
Traceback (most recent call last): … (401)
```

This is the "stale diagnostic that runs and lies" case the brief names — worse
than deleted, because the obvious reading of the traceback is *"Qdrant is
down"*, not *"this script is 40 commits stale"*. **Recommendation: fix it**
(add `api_key=settings.qdrant_api_key`, matching `qdrant_store.py:76`), don't
delete it — it is the only interactive way to look at what is actually stored.
One line, but it changes a file's behaviour from failing to working, so D5
applies.

### B-3 · Six stale documentation claims

Corrections, not deletions. Each is a claim a later commit made false:

| file | claim | reality |
|---|---|---|
| `FINAL_VERIFICATION.md:305` | *"(F3, open). The system is reproducible; its instrument is not yet."* | F3 fixed in `35ec4a2`; the instrument works |
| `FINAL_VERIFICATION.md:313` | *"387 passed / 1 skipped"* | 392 passed / 1 skipped |
| `RAG_FIELD_GUIDE.md:43` | *"tier B — 13 documents, 18 chunks · 15 of 22"* | 12 indexed documents, 17 chunks, 13 answerable |
| `rag_fact_sheet.yaml:142` | *"eval_corpus: … 13 documents"* | 13 in the corpus **definition**, 12 in the **index** — the distinction now matters |
| ~~`MANIFEST.yaml:38`~~ | *"tier A is NOT YET POPULATED"* | **WITHDRAWN — do not fix.** The pointer is stale, but `manifest_sha256` hashes the **whole file, comments included**. Editing the comment moved it `ccb0fba9…` → `f30fb62e…`, which is a HARD provenance field *and* the etag for every point ID: it would invalidate both reference baselines and force a full re-ingest. Attempted, measured, reverted. The cost of the fix exceeds the cost of the staleness by orders of magnitude (D6). |
| `HANDOFF.md:581` / `FINAL_VERIFICATION.md:264` | *"referenceless"* | both already read as past tense in context — **verified correct, no change needed** |

The field-guide headline (row 3) is the one that matters: it is the number a
reader takes away, and it now describes a corpus that is no longer indexed.

## 4 · Image analysis

**Measured before.**

| image | size | note |
|---|---|---|
| `knowall-documentbot-api` | 10.1 GB | |
| `knowall-documentbot-worker` | 10.1 GB | **same 16 layers, byte-identical** — verified via `RootFS.Layers`. The second image costs ~0 additional disk. |
| `knowall-documentbot-web` | 323 MB | already multi-stage (`deps` → `build` → `run`), nothing to reclaim |

So the honest figure is **~10.1 GB for the backend, not 20.2 GB.**

**Layer accounting for the 10.1 GB:**

| layer | size | verdict |
|---|---|---|
| model download + fastembed constructors | **4.49 GB** | **3.1 GB removable** (R-1) |
| `pip install -r requirements.txt` | 806 MB | required |
| `COPY . ./` | 63.6 MB | see note below |
| `apt-get install tesseract-ocr` | 104 MB | required; OCR is a shipped feature |
| `COPY vendor/tessdata/` | 37.7 MB | required and checksummed |
| debian base + toolchain | ~134 MB | base image, pinned by digest |
| `pip install --upgrade pip` | 19.2 MB | trivially foldable into the next layer; not worth a rebuild on its own |

**Estimated after R-1: ~7.0 GB** (10.1 − 3.1), a **31% reduction**. Build time
should also fall — three 1 GB downloads are avoided, though the exact saving
depends on the network and was not measured.

**On multi-stage for the backend:** examined and **not** recommended. The build
tooling that a multi-stage boundary would drop is in the pinned base image
(~41 MB of `gcc`/`dpkg-dev`), and the two things worth keeping out — the
duplicate weights — are better handled by R-1's single `rm -rf` than by
restructuring a Dockerfile whose every line carries a finding reference. The
cost/benefit is poor and the regression surface is not.

**`COPY . ./` at 63.6 MB** is larger than the source tree because it includes
`eval/corpus/` and `vendor/`. Both are *wanted* in the image — the eval harness
and OCR data run there. Not a finding.

## The method's error rate

Stated plainly, because it is the most transferable thing here.

| stage | candidates produced | survived investigation |
|---|---|---|
| zero-reference modules | 26 | 2 (24 were pytest-discovered tests) |
| unread `.env.example` variables | 6 | 0 (all pydantic-mapped) |
| unconsumed `Settings` fields | 2 | 0 (both `computed_field`) |
| frontend dependencies | 5 | 0 (all toolchain-implicit) |
| python dependencies | 5 | 1 (`minio`) |
| **total** | **44** | **3** |

**A 93% false-positive rate.** Every one of those 41 non-findings would have
looked like a finding in a report that stopped at the grep — which is exactly
what "70 dead, then 8, then 0" was, and what catalogue 19 describes. The
protection is not a better regex; it is that **absence of a match was never
accepted as evidence**, and each candidate was disproved by a different
mechanism than the one that produced it: pytest for collection, the dispatch
table for extensions, the lockfile for dependencies, `config.py` for settings,
and a throwaway container for the model cache.

The one item where the grep and the truth agreed — `minio` — is also the one
where the reverse-dependency check in the lockfile was needed to confirm it.

## Recommended sequence

One category per commit, CI green between each (D3).

1. **R-2** (`tsbuildinfo` + ignore rules) — smallest surface, no rebuild.
2. **B-2** (fix `check_qdrant.py`) — one line, restores a broken tool.
3. **B-1** (rename the two smoke scripts) — removes the collection hazard.
4. **B-3** (documentation corrections) — no code.
5. **R-1** (image prune) — **the one that matters.** Acceptance: image build
   green, `verify_model_pins.py` passes, `verify_ocr.py` passes, and a retrieval
   eval returns `COMPARABLE` against `tier-b-retrieval-2026-08-14.json` with
   deltas of 0.000.
6. **R-3** (`minio`) — last, because it requires regenerating a hashed lockfile.
7. **R-4** (dead images) — environment hygiene, by explicit ID, never a blanket
   prune.

Items 1–4 are reversible by `git revert`. Items 5–6 require a rebuild to roll
back. Item 7 requires a rebuild of the deleted images, which nobody needs.
